# 모바일 손가락 드로잉 PWA 구현 계획

## 현재 저장소 상태

- 기준 문서는 `모바일_손가락_드로잉_PWA_종합_기획서.docx` v1.0(2026-08-01)이며 본문 458개 문단과 12개 표 전체를 검토했다.
- React·TypeScript·Vite 기반 설치형 PWA와 자동/브라우저 테스트가 구현되어 있다.
- 앱 데이터는 IndexedDB에 프로젝트별 리비전과 이미지 Blob으로 저장된다.

## 구현 범위

기획서의 P0 전체와 일상 사용에 필요한 P1 일부를 다음 흐름으로 구현했다.

1. 앱 시작과 기본 1080×1080 흰색 작업 생성(기존 1080×1920 저장본은 원래 크기로 복구)
2. 한 손가락·마우스·펜의 Pointer Events 입력과 즉시 임시 스트로크 표시
3. 화면 좌표를 현재 보기 변환의 역행렬로 캔버스 좌표로 변환
4. 펜·연필·마커·붓·형광펜·스프레이·알파 지우개 7종의 확정 합성과 색상·도구별 굵기·농도 조절
5. 두 번째 포인터 진입 시 스트로크 안전 종료, 두 손가락 이동·핀치
6. 실행 취소·다시 실행과 새 작업 뒤 redo 초기화
7. 2초 디바운스, 15초 최대 간격, 숨김 전환 커밋을 포함한 IndexedDB 자동 저장
8. 이전 정상 리비전을 남기는 리비전 교체와 재실행 복구
9. 보기 변환과 무관한 전체 원본 크기의 PNG/JPEG 공유 또는 다운로드
10. 앱 셸 프리캐시, 매니페스트, 설치형 표시와 두 줄 모바일 퀵 도구 UI
11. 즉시 초기화하는 새 그림과 버튼·마우스 휠·두 손가락 확대/축소
12. 로컬 파일·드래그 앤 드롭·클립보드·URL·Android 공유 대상에서 이미지 가져오기, 맞춤/채우기와 90도 회전
13. 프로젝트 목록·복제·소프트 삭제, `.fingertip` 원본 파일 내보내기/불러오기
14. 최대 8개의 제한 레이어(추가·선택·표시·농도·순서·복제·삭제)와 배경 이미지 레이어
15. 손떨림 보정·스타일러스 압력·흐름/경도/간격, 스포이드, 색상 휠·즐겨찾기, 페인트통과 기본 도형
16. 마지막 도구·색상과 도구별 굵기·농도·고급 설정의 버전형 저장, 기존 설정 자동 이전과 모바일 재실행 복구

## 구현·검증 상태 (2026-08-01)

- 위 1~16 흐름을 애플리케이션 코드로 구현했다.
- TypeScript 검사, ESLint, 33개 단위 테스트, 프로덕션 빌드가 통과했다.
- 모바일 Chromium 브라우저 자동화 11개가 통과했다. 기존 페인팅 흐름에 버전형 도구 설정 이전, 새 그림·재실행 후 도구/굵기/색상/농도 복구와 고급 설정 복구를 추가했다.
- 390×844 세로와 844×390 가로 CSS px에서 도구가 겹치지 않고 첫 도구부터 노출되며, 넘치는 항목은 각 패널 안에서 스크롤 가능한 것을 시각·DOM 치수로 확인했다.
- 브라우저 자동화의 완전한 offline reload는 모듈 프리로드 요청을 서비스 워커보다 먼저 네트워크 실패로 처리하는 실행 환경 제약이 있었다. 캐시된 HTML·JS·CSS가 네트워크 차단 상태에서 각각 200으로 응답하는 것까지 자동 검증했고, 프로세스 종료 후 냉시작은 iOS/Android 설치 앱 실기기 항목으로 유지한다.

## 후속 P1/P2 범위

기획서가 P1/P2로 분리한 자유 각도 보기 회전, 돋보기, 왼손/한손/어린이 모드, 자유 변형 사진 배치, 캔버스 크기 변경, 선택 영역·필터는 이번 확장에서 구현하지 않았다. 레이어 구조 변경 자체를 한 번에 되돌리는 undo와 레이어 이름 변경·병합도 후속 범위다. 현재 UI에는 이 기능을 가장하는 비활성 버튼을 두지 않는다.

## 목표 아키텍처

### 핵심 모듈과 책임

- `drawing/model`: 작업, 스트로크, 샘플, 보기 변환과 직렬화 가능한 데이터 모델
- `drawing/coordinates`: 화면/캔버스 좌표 변환, 맞춤 변환과 확대 범위
- `drawing/inputMachine`: 대기, 단일 스트로크, 멀티터치 보기, 안정화 상태의 전환과 제스처 판정
- `drawing/renderer`: 확정 표면, 임시 표면, 표시 캔버스를 분리한 Canvas 2D 렌더링
- `drawing/history`: 스트로크 단위 undo/redo, 50단계 상한과 결정적 재생
- `persistence/database`: IndexedDB 스키마와 트랜잭션 경계
- `persistence/revisions`: pending 리비전 기록 후 complete 전환, 활성 리비전 교체, 이전 정상본 유지
- `persistence/autosave`: 변경 감지, 2초 디바운스, 15초 최대 지연, 즉시 커밋
- `export/png`: 전체 원본 크기 합성, Blob 생성, 공유 기능 감지와 다운로드 대체
- `pwa`: 서비스 워커 등록, 대기 업데이트 알림과 사용자 승인 적용
- `ui`: 저장 상태, 제목, 내보내기, 브러시 상태, 굵기, undo/redo를 표시하는 반응형 셸

Canvas 프레임은 React 상태 갱신과 분리한다. React는 툴바와 상태 레이블만 갱신하고 포인터 샘플과 캔버스 표면은 명령형 객체가 소유한다.

## 개발 단계와 완료 조건

### 1. 기반과 순수 로직

- React, TypeScript, Vite, ESLint, Vitest 기반을 만든다.
- 데이터 모델, 좌표 변환, 히스토리, 입력 상태 전환을 구현한다.
- 완료 조건: 좌표 왕복, 두 번째 포인터 진입, 임계값, 점 처리, redo 초기화 테스트가 통과한다.

### 2. 캔버스 입력과 보기 변환

- DPR 제한 표시 캔버스, 확정 오프스크린 표면, 임시 오버레이를 연결한다.
- rAF 큐에서 합쳐진 포인터 샘플을 처리한다.
- 포인터 캡처와 cancel/lost capture/회전/숨김 안전 종료를 연결한다.
- 완료 조건: 점·느린 선·빠른 선이 이어지고 핀치 중 브러시 점이 추가되지 않으며 resize 뒤 작업 데이터가 유지된다.

### 3. 저장·복구

- IndexedDB v1에 프로젝트와 리비전 저장소를 둔다.
- 매 저장마다 새 리비전을 pending으로 쓰고, 필수 데이터 기록 뒤 complete로 전환해 프로젝트의 활성 포인터를 바꾼다.
- 이전 정상 리비전 하나를 유지하고 불완전 리비전은 활성 후보에서 제외한다.
- 완료 조건: 새로고침 뒤 마지막 확정 스트로크와 undo 가능한 스트로크 모델이 복원되며 저장 실패가 입력을 막지 않는다.

### 4. PNG와 PWA

- 보기 행렬을 사용하지 않는 원본 크기 렌더로 PNG Blob을 만든다.
- 파일 공유가 가능한 환경은 공유하고, 취소는 조용히 종료하며, 그 외는 다운로드한다.
- 앱 셸과 동일 출처 정적 자산만 프리캐시한다. 사용자 작업은 Cache Storage에 넣지 않는다.
- 완료 조건: 새 작업 내보내기 크기가 1080×1080이고 오프라인 재시작 시 셸과 IndexedDB 작업이 열린다.

### 5. 제품 검증

- 타입 검사, 린트, 단위/통합 테스트, 프로덕션 빌드를 실행한다.
- 로컬 브라우저에서 드로잉, 핀치 상태 전환, 새로고침 복구, PNG 생성을 확인한다.
- 실기기에서만 확인 가능한 항목은 테스트 매트릭스에 분리한다.

## 테스트 전략

- 순수 단위 테스트: 행렬 역변환, 맞춤, 제스처 임계값, 상태 전환, 히스토리, 데이터 버전, 리비전 선택
- DOM 통합 테스트: 자동 저장 스케줄러, 공유/다운로드 분기, 서비스 워커 업데이트 메시지
- 브라우저 통합 테스트: 포인터 시퀀스, 캔버스 결과 변화, undo/redo, 새로고침 복구, PNG 픽셀 크기, 오프라인 재시작
- 수동 실기기: iOS Safari/홈 화면 앱, Android Chrome/설치 앱, 가장자리 제스처, 화면 회전, 백그라운드 강제 종료, 공유 시트

## 플래그별 검증

- `npm run test`: 순수 로직과 저장 선택 규칙
- `npm run lint`: 코드 품질과 React Hooks 규칙
- `npm run typecheck`: DOM·Canvas·IndexedDB 타입 안전성
- `npm run build`: 서비스 워커·매니페스트를 포함한 정적 프로덕션 산출물
- `npm run test:e2e`: 실제 브라우저 사용자 흐름

## 주요 위험

- iOS는 종료 시 비동기 IndexedDB 완료를 보장하지 않는다. 스트로크 저널을 자주 저장하고 `visibilitychange`에서 작은 커밋을 우선한다.
- 기존 1080×1920 원본과 오프스크린 표면은 약 8MB씩 필요하다. 표시 표면 DPR은 2로 제한하고 히스토리에 전체 래스터 복사본을 쌓지 않는다.
- 포인터 이벤트의 플랫폼 차이는 순수 상태 머신 테스트만으로 충분하지 않다. 실제 iOS/Android 제스처 회귀 시험이 필요하다.
- PNG 인코딩은 큰 캔버스에서 메인 스레드를 점유할 수 있다. 이번 슬라이스에서는 상태를 표시하고 입력 중 내보내기를 직렬화하며, 워커 인코딩은 후속 후보로 남긴다.
